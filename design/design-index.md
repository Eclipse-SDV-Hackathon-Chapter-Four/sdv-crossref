# Design patterns

The rest of the vault answers "what exists and how do I run it". This folder answers "how should I think about this problem, and who solved it before". One note per pattern, one screen each, written to the `_templates/pattern.md` shape: problem, forces, rule, prior art, how it lands on the Eclipse SDV stack, the trap, the hackathon-sized version, evidence.

## The lens: type, instance, placement

Most open-world modelling problems in a vehicle or a robot tangle three things that every good system keeps apart:

- **Type** is the closed world: the layout of one signal set or message, hashed, known at build time. Safety consumers only read types they were built against.
- **Instance** is the open world: which trailer, which gripper, which of a thousand vehicles. Instances arrive and leave at runtime and bring their own identity.
- **Placement** is who produces which set at which cadence on which node. In a static deployment it is written down; in a dynamic one it is announced.

Many patterns in the clusters below are special cases of keeping those three apart. The first card, [[instance-in-the-name-type-in-the-hash]], is the worked example.
