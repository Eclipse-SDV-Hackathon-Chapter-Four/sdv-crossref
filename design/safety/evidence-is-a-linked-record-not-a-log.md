# Evidence is a linked record, not a log

**Problem.** A team runs a fault campaign and shows a scrolling log. Nobody can say which hazard the run argued about, which safety goal it supports, which software version was under test, or whether running it again gives the same verdict. A safety case cannot cite a log; it cites records.

**Forces.**
- A safety case is an argument (hazard → safety goal → requirement → evidence); every arrow must be followable by an assessor who was not in the room.
- Logs are cheap and complete; records are expensive and selective.
- The detector (Guardian) must not be the only witness of its own success.
- Evidence must survive a rebuild: same inputs, same commit, same verdict.

**The rule.** One record per test, with an id for every link in the chain: `hazard_id → safety_goal_id → requirement_id → campaign_id/fault_id → detection_event_id → mitigation_event_id → verdict`, plus the build identity (commit, image digest), the injector's own timestamp, the detector's timestamp, and an independent oracle reading (SOVD fault state). "Evidence" means **linked** (ids, not prose), **timestamped** on a stated clock, and **reproducible** (the record names the campaign file and build that recreate it). The verdict is computed by comparing expectation (written before the run) with observation, never typed by hand. A log is raw material the record points into, not the record.

**Prior art.**
| Where | The idea | What it gives you |
|---|---|---|
| ISO 26262 (Parts 1–3, 8) | hazard analysis → safety goals (with ASIL) → functional/technical safety requirements → verification; safety case = argument + work products | the chain the record must mirror |
| ISO 21448 SOTIF | hazards from functional insufficiency, triggering conditions, known/unknown scenarios | a stuck sensor is ISO 26262; a correct sensor reading a misleading world is SOTIF; tag which |
| GSN Community Standard | goals, strategies, solutions (evidence nodes), context, explicit links | a machine-checkable shape for "this test supports that claim" |
| SLSA provenance / reproducible builds | signed statement binding artefact digest to source and build | "which software" becomes a digest, not a version string |
| S-CORE docs-as-code (sphinx-needs) | every requirement has `:id:`, `:safety:`, `:derived_from:`, `:satisfied_by:`, `:status:` | ready-made id scheme and link types to borrow |
| UN GTR No. 20 (EVS) | occupants warned of a thermal event (≥5 min before hazard in cabin) | a citable regulatory source for the Guardian's top-level safety goal |

**On the Eclipse SDV stack.** The challenge text already names the chain: "hazard → safety goal → injected fault → detection → mitigation → verdict" ([[chapter4-challenge-doctor-whodunit]]). Map it: hazard and safety goal live as sphinx-needs-style ids in the repo (borrow S-CORE's `stkh_req`/`feat_req` attribute set, [[s-core-overview]]); the fault id comes from the openDuT campaign YAML ([[opendut-overview]], executor is gap A6); detection and mitigation are uProtocol events carrying a correlation id in `traceparent` ([[uprotocol-howto]], schema gap A10); the oracle is SOVD `/components/<guardian>/faults` (gap A1) or a `triggers` hit (gap H2); the recorder that joins them is gap A5. Build identity: the AutoSD bootc image digest and the Ankaios manifest hash.

**The trap.** Letting the Guardian's own log be the evidence: the thing under test grading itself.

**For a hackathon team.** One JSON file per test with the seven ids, two clocks and a computed verdict, generated by the evidence collector; render the same JSON as a table. Pitch: "every fault leaves a record an assessor can follow without us in the room".

**Evidence.** ISO/SOTIF content from public ISO abstracts (clause numbers not verified). GTR 20 five-minute warning: globalautoregs summary (primary GTR text not read; unverified).
