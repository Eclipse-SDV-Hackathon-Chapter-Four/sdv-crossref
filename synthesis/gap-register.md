# Open problems you could solve (gap register)

An idea list for your team. Every item below is something that **does not exist today** in the Eclipse SDV ecosystem as far as the notes could establish (evidence linked), sized for a 2-day hackathon, and tagged with the challenge it serves. Evidence levels where given: R = reproduced here, C = read in upstream code or an issue, P = derived from a pattern card. Check the linked evidence yourself before you commit to a row: the ecosystem moves, and someone may have closed the gap since 2026-10-03.
Sizes: **S** = half a day for one person, **M** = one person-day, **L** = the whole team for two days (only sensible as *the* project).
Tags: DW = Doctor Whodunit, HF = Hack to the Future, FS = Freestyle track. ★ = also earns rubric bonus tech (openDuT, AutoSD, ThreadX, Jakarta EE).

How to use it: if you are stuck for an idea, pick one row from section A or B as your "innovation" and one row from section E as your guaranteed upstream contribution. If you already have an idea, use the register to check whether a piece you assume exists actually does. Ready-to-file issue drafts for many rows are in [[upstream-proposals]].

## H. Diagnostics, update and security plumbing (where OpenSOVD core is thin)

ISO 17978-3 defines far more resource collections than OpenSOVD core implements today (see the coverage table in [[opensovd-reference]]). Several are open upstream issues already, which makes them well-defined freestyle items; the rest are design patterns proven elsewhere that have no Eclipse implementation.

| # | Gap | Evidence | Size | Tags | Starter path |
|---|---|---|---|---|---|
| H1 | **`cyclic-subscriptions` over Server-Sent Events** in opensovd-core: create → 201 + Location, `GET` the subscription with `Accept: text/event-stream` to stream `{timestamp, payload, error}` envelopes. Nothing streams from core today; HackFest dashboards polled. | [[opensovd-reference]] (not implemented) | M | DW, FS | Broadcast channel per data resource; surface lag as an error envelope rather than dropping. |
| H2 | **`triggers` resource**: a condition (EnterRange / LeaveRange / OnChange / OnChangeTo) on a data resource fires an SSE event, a log entry, or a further SOVD command. This is the standard's own evidence hook and the natural home for "detection" in Doctor Whodunit. | [[opensovd-reference]] (not implemented) | M | DW, FS | Build on H1; a trigger that fires a `faults` entry (A1) closes the loop. |
| H3 | **`updates` resource** (register, prepare, execute, automated, status, delete) is open issue #195 in core. A banked implementation needs a state machine: queued → preparing → transferring → awaiting activation → awaiting reboot → verifying → activated → committed or rolled back, with an *orchestrated* mode that pauses at "awaiting verdict" until commit or rollback. | [[opensovd-reference]] (#195) | L | HF, FS | Keep the vendor verbs out of the standard surface: disclose extensions at a well-known endpoint using `x-<ext>-` names, never `x-sovd-`. |
| H4 | **Anti-rollback as a separate axis from build order.** A "security version" distinct from the sequence number lets a fleet A/B-test builds freely while a policy-only manifest raises the floor. No Eclipse update path (Symphony, Ankaios, Chapter 3 OTA) models this. | [[symphony-overview]], [[chapter3-retrospective]] | S (design) | HF, FS | Add `security_version` to whatever manifest the team ships; raise it only on commit, so trials stay revertible. |
| H5 | **Signed, encrypted update manifests (IETF SUIT)** have no Eclipse SDV implementation; only RFC 9019 (architecture) and RFC 9124 (information model) are published, while the manifest format, encryption and trust-domains are still IETF drafts (corrected 2026-10-03, see [[the-manifest-programs-the-device]]); Chapter 3's OTA used Symphony + Ankaios with no manifest signing. A two-level model (campaign manifest naming per-ECU image manifests, each signed by its author, payloads encrypt-once with per-device key wrapping) is the state of the art. | [[chapter3-retrospective]], [[symphony-overview]] | L | HF, FS | Smallest credible slice: COSE-signed image manifest with digest + security version, verified on the target before activation. |
| H6 | **Never mix revertible and irreversible components in one update transaction** (a VM bank can roll back; HSM key material cannot). The guard belongs in the orchestrator, not on the device. | none in any Eclipse note | S (rule) | HF | A pitch-grade invariant for any OTA story. |
| H7 | **Offline-verifiable SOVD client tokens**: ES256 JWT with an `x5c` chain to a *pinned* workshop CA, `aud` = vehicle id (replay guard across vehicles), per-component scopes; a small offboard minter publishes JWKS. OpenSOVD core has JWT + Rego hooks; the CDA accepts any credentials and signs with the literal key `secret`. | [[opensovd-quickstart]] (auth is demo-only) | M | DW, FS | Minter + verifier are a few hundred lines; refuse plaintext transport when auth is on. |
| H8 | **A parked vehicle has no trustworthy clock**, so every `exp` / `nbf` / certificate-validity check can be defeated by winding the clock back. A monotonic *time floor* ratcheted from signed artefacts (update manifests, tokens) and held in secure storage is the fix; no Eclipse component does it. Uptane 2.0 removed its time server: it recommends NTS, allows Roughtime and discourages GPS (corrected 2026-10-03, see [[time-only-moves-forward-from-signed-evidence]]). | [[opensovd-reference]] (JWT checks read the system clock) | M | FS | `now = max(now, floor)`; raise the floor only from signed sources. |
| H9 | **mDNS / DNS-SD discovery** (`_sovd._tcp`, `<id>.local`, TXT `accessurl` as an https URL) is mandatory in the standard and open issue #31 in core. TLS and discovery close as one gap because the advertised URL is https. | [[opensovd-reference]] (#31) | M | FS | Rust mDNS responder + the existing TLS listener. |
| H10 | **Capability description at `{path}/docs`** (OpenAPI 3.1 scoped to the path) is open issue #92 in core. | [[opensovd-reference]] (#92) | M | FS | Hand-maintained path table is acceptable; axum does not expose its route table. |
| H11 | **One server, one base path**: a proxy backend in core that fronts a CDA so `/sovd/v1` and `/vehicle/v15` stop being two worlds. The clean shape is one backend trait with UDS, gateway and proxy implementations behind one router. | [[opensovd-overview]] (two codebases, divergent paths) | M | DW, FS | Already a roadmap item ("gateway route forwarding to a CDA"); proxy is the smallest version. |
| H12 | **Vendor-free server, vendor extensions mounted by the integrator** and disclosed at `/.well-known/sovd-extensions`. OpenSOVD's `x-sovd2uds-*` routes follow the `x-<ext>-` rule but are not disclosed anywhere a scanner can enumerate. | [[opensovd-reference]] | S | FS | One JSON endpoint listing extension names and routes. |
| H13 | **SOVD `operations` in opensovd-core**: the home for a mitigation's status (started, running, completed, failed) as an addressable resource. Core has no `operations` collection. | [[mitigation-is-an-event-with-a-status]], [[opensovd-reference]] | M | DW, FS | Operation route per entity with an execution sub-resource whose status the Guardian updates; mirror the CDA's operation shape. |
| H14 | **Fleet-side presence**: birth/death of a vehicle over uProtocol or a Zenoh liveliness token. fleet-management has none; forwarder authorities are shared across trucks and a failed publish is dropped, so the backend cannot tell "silent" from "gone". | [[a-vehicle-is-gone-when-its-death-certificate-says-so]], [[authority-is-the-routing-unit]], [[sdv-blueprints-overview]] | M | FS | Per-VIN lowercase authority, a birth message on connect, a liveliness token whose loss is the death certificate. |
| H15 | **Geometry/calibration resource for trailer and body-builder sensors**: VSS carries values but no poses, so a sensor added by a body builder has no mounting frame anywhere in the model. | [[sensors-are-instances-calibration-is-data-tf-is-the-graph]] | M | HF, FS | Calibration as data per sensor instance (parent frame, translation, rotation), published as a static transform graph. |
| H16 | **Per-campaign evidence format** combining orchestrator workload states with each app's readiness claim, so a campaign verdict is a linked record rather than a log. | [[kill-restart-delete-are-test-actions]], [[one-supervisor-per-node-readiness-is-the-apps-claim]] | S | HF, DW, FS | One JSON record per campaign step: Ankaios workload state + app readiness + timestamps. |
